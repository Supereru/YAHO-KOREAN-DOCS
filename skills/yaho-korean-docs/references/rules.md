# 한국어 규칙집

기술 설명, 사용 안내, 업무 보고, 교육 자료를 명확하고 일관된 한국어로 작성하기 위한 실무 초안입니다[cite: 1]. ASD-STE100의 통제 언어(Controlled Language) 원칙을 바탕으로, 한국어 공공언어 작성 지침과 기술 용어의 의미 구분 기준을 결합했습니다[cite: 1]. 문장을 읽기 쉽게 다듬더라도 **원문의 사실관계와 기술적 동작을 그대로 유지하는 것**을 가장 중요한 기준으로 삼습니다[cite: 1].

작성일은 2026년 10월 7일입니다[cite: 1]. 이 문서는 공식 ASD-STE100 한국어판, 국가 표준, 인증 규격이 아니며, 원문 53개 규칙 전체의 일대일 번역이나 적합성 검증본도 아닙니다[cite: 1]. 아래의 36개 규칙과 예시는 이 초안을 위해 재구성한 한국어 기술 문서 작성 기준입니다[cite: 1].

함께 사용하는 자료는 [용어집 140개](glossary.md)와 [적용 지침](guidelines.txt)입니다[cite: 1]. 용어집은 사전 전체의 복제본이 아니라, 공인 자료에서 확인한 대응어와 자체 작성 기준을 구분하여 정리한 시작 목록입니다[cite: 1].

## 적용 대상과 우선순위

기본 적용 대상은 한국어로 작성하는 일반 기술 문서와 소프트웨어 안내문입니다[cite: 1]. 정비, 안전, 연구 분야에서는 해당 분야의 원문과 전문 정의를 우선합니다[cite: 1]. 이 초안은 기술적 내용을 새로 결정하거나 승인하는 기준이 아닙니다[cite: 1].

표현을 선택할 때는 다음 우선순위에 따라 판단합니다[cite: 1].

1. 원문의 의미, 수치, 조건, 예외, 부정, 책임 주체를 보존합니다[cite: 1].
2. 직접 인용문, 제품명, 화면 표시 텍스트(UI), 코드, 경로, 식별자 및 해당 분야에서 반드시 유지해야 하는 명칭을 보호합니다[cite: 1].
3. 해당 제품이나 기술 분야의 정의와 용어집을 따릅니다[cite: 1].
4. 국어사전과 어문 규범을 통해 일반어의 뜻과 표기를 확인합니다[cite: 1].
5. 의미가 완전히 같은 범위 안에서 더 쉽고 자연스러운 표현을 선택합니다[cite: 1].

순화어나 다듬은 말이 있다고 해서 원래 표현을 무조건 틀린 말로 취급하지 않습니다[cite: 1]. 용어집에 없는 표현도 자동으로 금지하지 않으며, 문맥상 실제 의미를 먼저 확인한 뒤 새 항목으로 추가해 관리합니다[cite: 1].

## 작성 규칙 36개

### 1. 의미와 용어

- **R01 의미 보존** — 원문의 사실, 대상, 조건, 예외, 부정, 순서, 가능성, 수치와 단위를 바꾸지 않습니다[cite: 1]. 문장을 간결하게 줄인다는 이유로 필수 정보를 삭제하지 않습니다[cite: 1].
- **R02 보호 구간 유지** — 직접 인용, 코드, 명령어, 파일명, 경로, 변수명, 모델명, 표준 식별자 및 화면의 실제 표시 이름(UI 텍스트)은 임의로 번역하거나 고치지 않고, 주변 설명을 쉽게 풀어 씁니다[cite: 1].
- **R03 개념별 대표 용어** — 같은 분야의 같은 개념에는 대표 용어 하나를 정해 일관되게 씁니다[cite: 1]. 철자가 같은 단어라도 분야나 뜻이 다르면 별도 항목으로 분리해 관리합니다[cite: 1].
- **R04 조건부 대응** — 단어만 보고 기계적으로 치환하지 않습니다[cite: 1]. 용어집에 정의된 분야, 뜻, 적용 조건, 예외 사항을 먼저 확인한 뒤 적용합니다[cite: 1].
- **R05 전문용어 유지** — 쉬운 말로 바꿨을 때 기술적 정의나 범위가 달라진다면 전문용어를 그대로 유지하고, 필요한 경우 처음 등장할 때 짧게 풀어서 설명합니다[cite: 1].
- **R06 약어 소개** — 독자에게 낯선 약어는 처음 나올 때 원래 의미를 풀어 씁니다[cite: 1]. 단, 독자에게 이미 익숙한 약어까지 매번 풀어 쓰지는 않으며, 한 약어가 두 가지 이상의 뜻으로 쓰이면 문맥을 명시합니다[cite: 1].
- **R07 표기 및 문장 부호 확인** — 일반어는 국어사전과 어문 규범을 기준으로 표기를 확인하며, 사전에 등재되지 않았다는 이유만으로 오자로 단정하지 않습니다[cite: 1]. 특정 제품이나 기술 분야에서 정한 표기가 있으면 그 근거를 기록합니다[cite: 1]. 단어를 나열할 때는 의미 관계를 모호하게 만드는 중간점(가운뎃점)을 사용하지 않고 쉼표(,), '와/과', '및', '또는'을 사용합니다.
- **R08 명사 관계 표시** — 여러 명사를 조사 없이 길게 이어 쓰지 않습니다[cite: 1]. 예를 들어 ‘사용자 권한 변경 이력 확인’은 ‘사용자의 권한 변경 이력을 확인합니다’처럼 의미 관계를 드러내어 풀어 씁니다(단, 짧고 명확한 제목이나 표 머리글은 명사형 허용)[cite: 1].

### 2. 문장과 논리

- **R09 필요한 주체 명시** — 동작의 주체(사용자, 관리자, 시스템 등)가 누구인지 혼동될 때는 주어를 명시합니다[cite: 1]. 반면 사용자에게 작업을 지시하는 절차문에서 주체가 자명할 때는 ‘사용자는’을 불필요하게 반복하지 않습니다[cite: 1].
- **R10 대상 명시** — ‘이것’, ‘해당 항목’, ‘이를’ 같은 지시어가 가리키는 대상이 모호하면 실제 대상 이름을 적습니다[cite: 1]. 대상이 문맥상 명확할 때는 한국어 어법에 맞게 자연스러운 생략을 허용합니다[cite: 1].
- **R11 중심 내용 하나** — 한 문장에 서로 다른 설명이나 결론을 여러 개 섞어 넣지 않습니다[cite: 1]. 논리 관계가 깨지지 않는 선에서 문장을 나눕니다[cite: 1].
- **R12 조건과 예외 연결** — 동작이 실행되는 조건은 해당 동작 앞에 제시하고, 예외 사항은 영향을 받는 동작 바로 가까이에 둡니다[cite: 1]. 하나의 조건이 여러 단계에 걸쳐 적용된다면 그 적용 범위를 분명히 밝힙니다[cite: 1].
- **R13 논리 연산 보존** — ‘모두(AND)’, ‘하나 이상(OR)’, ‘오직’, ‘제외(NOT)’, ‘그리고’, ‘또는’의 논리 관계를 명확히 구분합니다[cite: 1]. 중간점(가운뎃점)으로 단어들을 묶어 ‘그리고’와 ‘또는’의 관계를 뭉뚱그리지 않습니다. 원문의 ‘또는’이 포괄적 선택(하나 이상)인지 배타적 선택(둘 중 하나만)인지 불분명할 때는 임의로 단정하지 않습니다[cite: 1].
- **R14 시점과 상태 보존** — 작업의 예정, 진행 중, 완료, 실패 상태를 엄격히 구분합니다[cite: 1]. 예를 들어 ‘저장합니다’를 근거 없이 완료형인 ‘저장했습니다’로 바꾸지 않습니다[cite: 1].
- **R15 필요한 피동 허용** — 동작의 주체를 알고 있고 그 주체가 중요할 때는 능동문을 우선합니다[cite: 1]. 그러나 주체를 알 수 없거나 동작의 결과와 상태 자체가 중심일 때는 피동문을 허용하며, 억지로 능동문을 만들기 위해 원문에 없는 행위자를 추측해 넣지 않습니다[cite: 1].
- **R16 자연스러운 동사 사용** — ‘확인을 수행합니다’, ‘변경을 진행합니다’ 같은 번거로운 명사+동사 구성은 ‘확인합니다’, ‘변경합니다’처럼 자연스러운 동사로 줄여 씁니다[cite: 1]. 단, 공식적으로 정의된 작업명이나 명사형이 필요한 제목까지 일괄 수정하지는 않습니다[cite: 1].
- **R17 길이보다 구조 점검** — 한국어 문장의 어절 수 상한선을 기계적으로 고정하지 않습니다[cite: 1]. 대신 지나치게 긴 관형절(수식어), 중첩된 조건절, 끝없이 이어지는 연결 어미가 독자의 이해를 방해하지 않는지 문장 구조를 점검합니다[cite: 1].
- **R18 문체 일관성** — 일반 설명은 ‘~합니다’, 정식 절차의 지시문은 ‘~하십시오’를 기본으로 삼으며, 대화형 인터페이스나 친근한 안내문에서는 ‘~하세요’를 쓸 수 있습니다[cite: 1]. 문체는 독자와 매체 특성에 맞추되 하나의 문서나 기능 안에서는 일관되게 통일합니다[cite: 1].

### 3. 절차와 화면 안내

- **R19 수행 단위로 나누기** — 독립적으로 수행하거나 완료 여부를 확인할 수 있는 작업은 번호를 매겨 단계별로 나눕니다[cite: 1]. 단, 동시에 수행해야 하는 동작은 두 단계로 쪼개지 않고 동시성을 그대로 유지합니다[cite: 1].
- **R20 준비 조건 선행** — 작업을 시작하기 전에 필요한 파일, 권한, 연결 상태, 도구를 절차 앞에 먼저 제시합니다[cite: 1]. 원문에 없는 준비 조건을 임의로 추측해 필수 사항으로 추가하지 않습니다[cite: 1].
- **R21 사용자 동작과 시스템 결과 구분** — 사용자의 조작(‘저장 버튼을 누르십시오’)과 시스템의 반응(‘시스템이 설정을 저장합니다’)을 명확히 구분합니다[cite: 1]. 시스템의 후속 동작이 확인되지 않은 상태에서 결과를 임의로 단정해 적지 않습니다[cite: 1].
- **R22 화면 이름 일치** — 버튼이나 메뉴 이름은 실제 화면에 표시되는 텍스트와 정확히 일치시킵니다[cite: 1]. 화면에 ‘Apply’라고 적힌 버튼을 안내문에서 임의로 ‘저장’이라 부르지 않으며, 설명이 필요하면 ‘Apply(적용)’처럼 병기합니다[cite: 1].
- **R23 입력 방식 구분** — 일반적인 버튼 조작 안내에는 ‘누르다’를 쓸 수 있습니다[cite: 1]. 하지만 마우스 클릭, 두 번 클릭(더블클릭), 길게 누르기, 키보드 입력처럼 조작 방식에 따라 결과가 달라질 때는 정확한 입력 방식을 명시합니다[cite: 1]. ‘선택하다’는 목록이나 옵션을 고르는 동작에 한정하며 실행이나 제출 동작과 구분합니다[cite: 1].
- **R24 완료 기준 명시** — 원문에 제시된 성공 메시지, 표시 상태, 생성된 결과 파일 등 작업 완료의 근거를 그대로 유지합니다[cite: 1]. 단순히 화면이 넘어갔다는 이유만으로 저장이나 제출이 성공했다고 단정하지 않습니다[cite: 1].
- **R25 실패 안내 구체화** — 실제로 확인된 실패 현상과 사용자가 취할 수 있는 다음 행동을 구분해 적습니다[cite: 1]. 원인이 명확히 확인되지 않았다면 추정 원인을 확정된 사실처럼 서술하지 않습니다[cite: 1].
- **R26 위험과 데이터 영향 유지** — 삭제, 초기화, 덮어쓰기, 권한 변경에 따른 데이터 손실 영향, 경고, 복구 조건을 생략하지 않습니다[cite: 1]. 위험 정보는 해당 작업 단계보다 앞에 배치하되, 별도의 기술 검토 없이 새로운 위험 등급을 임의로 만들지 않습니다[cite: 1].

### 4. 수치와 요구 수준

- **R27 값과 단위 결합** — 수치, 단위, 비교 기준, 측정 조건을 빠짐없이 함께 유지합니다[cite: 1]. 단순한 문장 다듬기 과정에서 단위를 임의로 변환하거나 수치를 반올림하지 않습니다[cite: 1].
- **R28 경계 포함 여부 보존** — 경계값을 포함하는 ‘이상, 이하’와 포함하지 않는 ‘초과, 미만’을 엄격히 구분합니다[cite: 1]. 부등호 기호를 문장으로 풀어 쓸 때도 경계값 포함 여부를 반드시 확인합니다[cite: 1].
- **R29 비율 구분** — 상대적인 비율(%)의 변화와 산술적인 퍼센트포인트(%p)의 차이를 명확히 구분합니다[cite: 1]. 예를 들어 ‘20%에서 30%로 증가’를 ‘10% 증가’로 잘못 줄여 쓰지 않으며, 별도 산출이 허용된 경우에만 상대 증가율(50% 증가)이나 퍼센트포인트(10%p 증가)를 계산해 적습니다[cite: 1].
- **R30 날짜와 기준 시점 명시** — 배포 후 독립적으로 읽히는 문서에서 ‘내일’, ‘다음 주’처럼 기준 시점이 사라지는 상대적 시간 표현은 구체적인 날짜를 병기합니다[cite: 1]. 단, 원문에 기준 날짜나 시간대(Time zone) 정보가 없다면 임의로 추측해 적지 않습니다[cite: 1].
- **R31 의무와 권장 구분** — 필수 의무는 ‘~해야 합니다’, 금지는 ‘~해서는 안 됩니다’, 권고 사항은 ‘~권장합니다’로 명확히 구분합니다[cite: 1]. 말투를 부드럽게 다듬는다는 이유로 필수 요구 수준을 권장 수준으로 낮추지 않습니다[cite: 1].
- **R32 가능과 허용 구분** — 시스템 기능과 능력은 ‘~할 수 있습니다’, 정책상 허용은 ‘~해도 됩니다’, 사건 발생 가능성은 ‘~발생할 수 있습니다’로 구분해 표현합니다[cite: 1]. 원문의 ‘~할 수 있다’가 어떤 뜻인지 모호할 때는 임의로 바꾸지 않고 의미를 먼저 확인합니다[cite: 1].

### 5. 문서 구성과 검토

- **R33 목적과 핵심 먼저** — 문서나 절의 첫 부분에 독자가 얻을 결과나 수행해야 할 핵심 작업을 먼저 제시합니다[cite: 1]. 작업 절차에서는 필수 전제 조건과 안전 경고가 실제 행동 지시보다 뒤로 밀리지 않게 배치합니다[cite: 1].
- **R34 비교 가능한 구조** — 작업 순서는 번호 목록(1, 2, 3), 대등한 선택지는 글머리표(-), 반복되는 속성의 비교는 표(Table)를 사용합니다[cite: 1]. 인과 관계나 논리적 흐름이 중요한 설명은 완결된 문장으로 풀어서 씁니다[cite: 1].
- **R35 불확실성 유지** — ‘추정’, ‘예상’, ‘관측’, ‘검증’, ‘완료’의 단계를 명확히 구분합니다[cite: 1]. 문장을 명쾌하게 쓴다는 이유로 근거 없는 확신을 덧붙이지 않습니다[cite: 1].
- **R36 수정 후 대조** — 문장을 다듬은 뒤에는 원문과 수정문의 수치, 단위, 부정어, 조건, 예외, 순서, 주체, 기술용어를 일대일로 대조합니다[cite: 1]. 원문 자체가 모호해 해석이 갈리는 항목은 임의로 고치지 않고 별도의 ‘확인 필요 사항’으로 남깁니다[cite: 1].

## 용어집 사용 방법

용어집의 각 항목은 식별자(ID), 입력 표현, 권장 표현(또는 처리 방식), 적용 조건과 예외, 근거 상태를 갖습니다[cite: 1]. ‘권장 표현’은 문맥을 무시하고 무조건 바꿔야 하는 기계적 치환어가 아닙니다[cite: 1].

| 처리 유형 | 적용 방법 |
| --- | --- |
| 조건부 변경 | 문맥상 뜻과 적용 조건이 완전히 일치할 때만 권장 표현으로 고칩니다[cite: 1]. |
| 유지 후 설명 | 전문용어를 그대로 유지하되, 독자의 이해를 돕기 위해 필요한 설명을 덧붙입니다[cite: 1]. |
| 구분해서 사용 | 비슷해 보이지만 서로 다른 기술 개념을 각각의 정확한 이름으로 구분해 씁니다[cite: 1]. |
| 확인 필요 | 원문만으로 정확한 뜻을 확정할 수 없으면 수정하지 않고 확인 항목으로 남깁니다[cite: 1]. |

공식 자료에서 확인한 대응어라도 이 초안에서 정한 사용 조건에 부합할 때만 적용하며, 자체 제안 표현을 국가 공인 순화어나 분야 표준인 것처럼 표시하지 않습니다[cite: 1].

## 처음 초안에서 보완한 부분

- ‘클릭, 누르기, 선택’은 항상 동의어가 아니므로 입력 방식과 선택 동작을 구분합니다[cite: 1].
- ‘~하십시오’를 모든 문서에 강제하지 않고, 설명서, 대화형 안내, 화면 텍스트의 문체를 상황에 맞게 구분합니다[cite: 1].
- 모든 피동문을 기계적으로 제거하지 않음으로써, 원문에 없는 행위자가 임의로 추가되는 왜곡을 막습니다[cite: 1].
- ‘한 단어 한 의미’ 원칙을 언어 전체에 무리하게 강제하지 않고, 기술 분야와 개념 단위로 의미를 관리합니다[cite: 1].
- ‘한 단계 한 동작’ 원칙을 적용하더라도 동시에 수행해야 하는 조작을 순차 동작으로 쪼개지 않습니다[cite: 1].
- ‘더 쉽다’는 이유로 ‘저장’을 ‘적용’으로, ‘인증’을 ‘인가’로 섞어 쓰지 않습니다[cite: 1].
- 단어 나열 시 의미 관계를 모호하게 만드는 중간점(가운뎃점)을 사용하지 않고, 쉼표(,), ‘와/과’, ‘및’, ‘또는’으로 관계를 명확히 드러냅니다.

## 적용 전후 예시 12개

아래 예시는 규칙 적용 방식을 보여주기 위해 작성한 가상의 문장이며, 특정 제품의 실제 동작 지침이 아닙니다[cite: 1].

### 예시 1: 불필요한 명사 표현 줄이기 (R16)
- **원문:** 설정값의 확인을 수행하십시오[cite: 1].
- **수정:** 설정값을 확인하십시오[cite: 1].
- **해설:** 동작과 대상은 그대로 유지하면서 번역투의 명사+동사 구성(‘확인을 수행하다’)을 간결한 동사로 줄였습니다[cite: 1].

### 예시 2: 독립된 작업 단계 나누기 (R19)
- **원문:** 파일을 열고 이름을 수정한 뒤 저장하십시오[cite: 1].
- **수정:**
  1. 파일을 여십시오[cite: 1].
  2. 이름을 수정하십시오[cite: 1].
  3. 파일을 저장하십시오[cite: 1].
- **해설:** 원문의 작업 순서를 유지하며 단계별로 나누었습니다[cite: 1]. 만약 실제 문서에서 ‘이름’이 파일명인지 파일 내부의 항목 이름인지 모호하다면 대상을 먼저 확인해 구체적으로 적어야 합니다[cite: 1].

### 예시 3: 동작보다 조건을 먼저 제시하기 (R12)
- **원문:** 다시 시도하십시오. 단, 연결 상태가 정상인 경우에만 가능합니다[cite: 1].
- **수정:** 연결 상태가 정상이면 다시 시도하십시오[cite: 1].
- **해설:** 사용자가 행동을 취하기 전에 전제 조건을 먼저 확인할 수 있도록 조건절을 앞으로 옮겼습니다[cite: 1].

### 예시 4: 동시 동작 보존하기 (R19, R23)
- **원문:** Shift 키를 누른 상태에서 파일을 클릭하십시오[cite: 1].
- **수정:** Shift 키를 누른 상태에서 파일을 클릭하십시오 (원문 유지)[cite: 1].
- **해설:** 동시에 수행해야 하는 조작이므로 ‘1. Shift 키를 누릅니다 / 2. 파일을 클릭합니다’처럼 순차 단계로 나누지 않습니다[cite: 1].

### 예시 5: 저장과 적용 구분하기 (R03, R22)
- **원문:** 설정을 저장한 후 적용 버튼을 클릭하십시오[cite: 1].
- **수정:**
  1. 설정을 저장하십시오[cite: 1].
  2. 적용 버튼을 클릭하십시오[cite: 1].
- **해설:** 서로 다른 기능인 ‘저장(보관)’과 ‘적용(반영)’을 하나의 단어로 합치지 않고 단계별로 명확히 구분합니다[cite: 1].

### 예시 6: 전문용어의 문맥 의미 풀어 쓰기 (R04, R05)
- **원문:** 인증된 사용자라도 인가되지 않은 파일은 읽을 수 없습니다[cite: 1].
- **수정:** 사용자 인증을 마쳤어도 읽기 권한이 없는 파일은 읽을 수 없습니다[cite: 1].
- **해설:** 이 문장에서 ‘인가(Authorization)’의 대상은 파일 읽기이므로, 일반 독자가 이해하기 쉽게 ‘읽기 권한’으로 풀어 썼습니다 ([개념 확인][S06])[cite: 1].

### 예시 7: 수치의 경계값 보존하기 (R28)
- **원문:** 온도가 80 °C를 초과하면 작동을 중지합니다[cite: 1].
- **수정:** 온도가 80 °C를 초과하면 작동을 중지합니다 (원문 유지)[cite: 1].
- **해설:** ‘80 °C 이상’으로 바꾸면 80 °C 정각일 때의 작동 조건이 달라지므로 원문 표현을 유지합니다[cite: 1].

### 예시 8: 가능성과 불확실성 보존하기 (R35)
- **원문:** 이 설정은 처리 시간을 줄일 수 있습니다[cite: 1].
- **수정:** 이 설정은 처리 시간을 줄일 수 있습니다 (원문 유지)[cite: 1].
- **해설:** 가능성을 나타내는 표현을 ‘처리 시간을 줄입니다’처럼 확정된 사실로 단정하지 않습니다[cite: 1].

### 예시 9: 행위자 임의 추측 금지 (R15)
- **원문:** 파일이 삭제되었습니다[cite: 1].
- **수정:** 파일이 삭제되었습니다 (원문 유지)[cite: 1].
- **해설:** 누가 삭제했는지 원문에 나와 있지 않은 상태에서 피동문을 없앤다는 이유로 ‘사용자가 파일을 삭제했습니다’라고 바꾸지 않습니다[cite: 1].

### 예시 10: 모호한 동작 지시 보류하기 (R04, R25)
- **원문:** 오류가 발생하면 적절히 처리하십시오[cite: 1].
- **수정:** (원문 유지 후 확인 요청)[cite: 1]
  - *확인 필요 사항:* 구체적으로 어떤 오류가 발생했을 때 무슨 조치를 취해야 하는지 원문 작성자의 확인이 필요합니다[cite: 1].
- **해설:** ‘적절히 처리’라는 모호한 말을 없애기 위해 작성자가 임의로 ‘재시작하십시오’나 ‘파일을 삭제하십시오’ 같은 지시를 지어내지 않습니다[cite: 1].

### 예시 11: 실제 화면 이름 보존하기 (R21, R22)
- **원문:** Apply를 클릭하면 변경된 설정이 적용됩니다[cite: 1].
- **수정:** Apply(적용)를 클릭하면 변경된 설정이 적용됩니다[cite: 1].
- **해설:** 실제 화면의 버튼 이름(Apply)을 보존하면서 괄호 안에 한국어 설명만 덧붙입니다[cite: 1]. 또한 조건부 동작 설명을 무조건 실행하라는 지시문으로 바꾸지 않습니다[cite: 1].

### 예시 12: 비율과 퍼센트포인트 보존하기 (R29)
- **원문:** 오류율이 20%에서 30%로 증가했습니다[cite: 1].
- **수정:** 오류율이 20%에서 30%로 증가했습니다 (원문 유지)[cite: 1].
- **해설:** 원래 수치만으로 의미가 명확하므로 불필요한 계산을 덧붙이지 않으며, 특히 ‘10% 증가’라는 잘못된 표현으로 줄이지 않습니다[cite: 1].

## 검토 절차

1. 문서의 대상 독자와 용도를 먼저 파악합니다(불분명할 경우 일반 기술 설명문을 기준으로 삼음)[cite: 1].
2. 직접 인용, 코드, 화면 표시 이름(UI), 수치와 단위, 핵심 전문용어를 보호 대상으로 표시합니다[cite: 1].
3. 문장마다 주체, 대상, 조건, 동작, 결과 성분이 명확한지 확인합니다[cite: 1].
4. 용어집에서 해당 기술 분야와 문맥상 의미가 일치하는 항목만 선별해 적용합니다[cite: 1].
5. 규칙에 맞춰 문장을 다듬고 작업 절차와 설명 구조를 정돈합니다[cite: 1].
6. 원문과 수정문을 대조하여 사실관계나 조건이 달라지지 않았는지 검증합니다[cite: 1].
7. 최종 수정문과 함께, 원문이 모호하여 추가 확인이 필요한 사항을 구분해 제시합니다[cite: 1].

### 완료 점검표 (체크리스트)

- [ ] 같은 대상을 문서 끝까지 같은 이름으로 일관되게 썼습니다[cite: 1].
- [ ] 보호 대상(코드, 고유명 등)과 수치 및 단위를 온전히 보존했습니다[cite: 1].
- [ ] 조건, 예외, 부정, 작업 순서가 원문 그대로 유지되었습니다[cite: 1].
- [ ] 중간점(가운뎃점)을 쓰지 않고 쉼표(,), '와/과', '및', '또는'으로 나열 관계를 분명히 적었습니다.
- [ ] 의무, 권장, 가능, 허용의 요구 수준 차이가 유지되었습니다[cite: 1].
- [ ] 원문에서 확인되지 않은 주체, 원인, 결과를 임의로 추가하지 않았습니다[cite: 1].
- [ ] 실제 화면(UI)의 명칭과 문서 내 표기가 일치합니다[cite: 1].
- [ ] 뜻이 모호한 단어는 문맥을 확인했거나 별도의 확인 필요 사항으로 남겼습니다[cite: 1].
- [ ] 전문용어를 쉽게 풀어 쓰면서 원래 개념의 범위를 넓히거나 좁히지 않았습니다[cite: 1].
- [ ] 문체(~합니다 / ~하십시오 / ~하세요)가 독자와 매체에 맞고 일관됩니다[cite: 1].
- [ ] 이 초안의 점검을 통과했다는 사실을 공식 ASD-STE100 인증으로 표시하지 않았습니다[cite: 1].

## 출처와 확인 범위

자료 확인일은 2026년 10월 7일입니다[cite: 1]. 사전과 목록의 존재를 확인한 것과 개별 용어의 의미를 확인한 것을 구분해 기록하며, 발행 시점이 오래된 자료는 현재 기술 분야에서의 실제 쓰임새를 함께 고려해야 합니다[cite: 1].

- **S01** [ASD About STE][S01]: 작성 규칙과 통제 사전의 결합 구조를 참고했습니다[cite: 1]. 공식 사이트의 소개 본문을 확인했으며, Issue 9 전체 PDF 원문을 일대일로 대조하지는 않았습니다[cite: 1].
- **S02** [문화체육관광부 및 국립국어원 쉬운 공공언어 쓰기 길잡이][S02]: PDF 본문과 34쪽 점검표를 확인했습니다(발행일: 2014년 5월)[cite: 1].
- **S03** [국립국어원 유형별로 알아보는 보도자료 작성 길잡이][S03]: PDF 108~110쪽의 용어 대응표를 확인해 일부 대응어를 선별했으며, 적용 조건과 예시는 이 초안에서 새로 작성했습니다[cite: 1].
- **S04** [국립국어원 다듬은 말 목록][S04]: 순화어 조회 방식을 확인했으며, 전체 목록을 일괄 검토하거나 반영한 것은 아닙니다[cite: 1].
- **S05** [국립국어원 인터페이스 항목][S05]: ‘접속 장치’ 대응어와 과거 이력을 확인하고, UI 및 API 문맥에 일괄 치환되지 않도록 예외 규칙을 두었습니다[cite: 1].
- **S06** [TTA 인가][S06]: 식별, 인증, 인가의 개념 차이를 확인했습니다(사전의 상세 설명은 복제하지 않음)[cite: 1].
- **S07** [TTA 응용 프로그래밍 인터페이스][S07]: API의 표제어와 기본 정의를 확인했습니다[cite: 1].
- **S08** [TTA 디지털 아카이브][S08]: 장기 보존용 아카이브와 재해 복구용 백업의 목적 차이를 확인했습니다(TTA 시사용어 자료)[cite: 1].
- **S09** [TTA 소프트웨어 설명의 백업과 복원 부분][S09]: 백업과 복원의 개념 구분을 확인했습니다[cite: 1].
- **S10** [Microsoft language resources][S10]: 제품 용어와 UI 문자열을 구분해 참고하는 원칙을 확인했습니다(한국어 스타일 가이드 전체나 용어 DB 전체를 가져온 것은 아님)[cite: 1].
- **S11** [표준국어대사전][S11]: 일반어의 표기와 뜻을 확인하는 공식 조회 경로입니다(초안의 모든 자체 제안을 사전에서 개별 검증한 것은 아님)[cite: 1].
- **S12** [국립국어원 외래어 표기법][S12]: 외래어 표기 확인 경로이며, 기술 개념의 동일성까지 보장하는 자료는 아닙니다[cite: 1].
- **S13** [국립국어원 온용어 도움말][S13]: 전문용어 검색 및 용어집 기능을 참고했으며, 개별 항목을 이번 용어집의 직접 근거로 사용하진 않았습니다[cite: 1].
- **S14** [국립국어원 한국어기초사전 가이드라인][S14]: ‘가이드라인’의 기본 의미(‘지침’)를 확인했습니다(문서별 강제성 여부는 개별 문서 기준에 따름)[cite: 1].
